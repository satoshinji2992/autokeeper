# 模型与 Agent 运行机制

`src/autokeeper/harness/` 负责模型调用、上下文、结构化输出、工具循环、搜索、预算和追踪。各后端提供统一的文本或 JSON 接口，游戏状态和规则结算由引擎管理。

对话记录随存档保存，中途可以切换模型。配置本地模型并关闭搜索后可离线运行；需提前安装依赖和下载模型。调用日志记录 token、缓存命中、延迟、输出修复和估算花费。

截至 0.0.4，KP 已读取模组底牌与本局幕后简报，统一理解玩家行动、安排在场 NPC 的主动参与，并通过场面快照与世界操作提交结果。裁定员不读取玩家原话；NPC 演出保留自己的知识范围，同时提交台词与动作。原文检索与当前改写可以并用，冲突时以本局改写为准。

确定结果的日程由代码执行；需要判断的幕后动向由触发条件唤醒，同一时间片的相关 NPC 集中在一次世界推演中处理。导演另在长途赶路、过夜等时机检查局势，也负责准备即兴内容。调度、待呈现的幕后变化与提交检查仍在代码中，不能把早期“全部撤除”的方案当成已完成事实。历史决策见[开发记录](development-notes-2026-10-20.md#当前架构决策kp记录库与模组日程)，版本变化见[更新记录](../CHANGELOG.md)。

运行时核对场面快照与操作，失败时带具体原因修正一次；未落实事项保留原因供后续处理。叙述、NPC 回应、掷骰与结算分阶段留下恢复记录。语义与文风的质量仍需定向模型测试、连续重放和实际游玩验证，不能仅凭结构校验通过判断。

KP 可以在同一次场面输出的 `scene.flags` 中提交已经发生的模组剧情事实，不再只靠骰前裁定预设人物回应后的结果。标记只接受模组已声明的编号，场面未完整落实时不提交。系统复用世界操作、事件和结局结算；若因此发生新的事件，其表演与后续叙述保存在同一回合的恢复记录中，不重做原行动，也不另设审稿角色。普通回合不因此增加调用。

KP 明确让待演安排抢先发生时，公开变化先展示，再按改变后的现场裁定；已经离场的人不能仍被当作站在面前掷交涉。普通闲聊可以仅以 NPC 回应结束，但有交易、等待或后续动作的日常行动仍交给 KP 完整演出。物品操作按实际实体编号或唯一显示名统一定位，文字记录“已归还”不能代替实际转交。

骰后的 NPC 回应由同一 KP 主持会话选择，不再直接执行骰前的主动安排。有主检定或重复检定时，KP 先读最终结果与当前现场，再返回一个 `HostedReply(kind="npc")`，指定人物、可感知情境与本次演出范围；宿主复用既有 NPC 回复、实际操作、知情与事件通路，将真实结果送回同一会话。KP 可以不采用旧安排，也可以改请另一个在场人物参与。无骰日常对白保留直接回应的短路径，裁定前的抢先反应仍先发生。

每次工具请求先保存，再执行；恢复沿同一编号及 `Said` 续接。工具结果进入 KP 正式历史，后续调用更新世界与场面资料，不能继续使用交物前的归属或离场前的人物清单。实际台词只在当次工具回执中写一份，附真实听众、已披露内容、成功提交的操作与未落实原因。首次主持保留行动结算，后续历史只追加新回执，不再每次保存完整报告和累计回执。当前调用仍读取完整最新报告；不是靠少交现场资料去重。私下配音、材料、日志和重连沿同一受众投递。

最终 `kind="tell"` 先保存完整稿件与记忆，再落实场面、个人知觉、休息和到访，最后登记正式正文并交付；中间工具请求不流入旁白框。普通纯文本仍可实时流式显示。正文开始、内容、结束，私有观察与媒体分别记录已返回的通知；传输失败从原稿续接，不重新问 KP、重骰或重演人物。存档日志与实时事件共用 `delivery` 标识，终端重试、联机重连复用同一正文块。通知返回不等于远端已经确认收到，未确认边界可能重交缓存内容，不能宣称网络恰好投递一次。

已保存稿件提交时若遇到真实世界冲突，保留实际成立的操作，未成立的成功稿不公开，由同一 KP 根据当前记录修正；原行动、骰和配音不重做。部分移动已经发生时，到访及其事件仍沿原结算日记处理和恢复。这里没有新增审核角色，也不对正文删句。结局仍保留本人观察和材料，但不借此提交新的场面操作；“改讲法”使用最终完整报告及对应增量记忆，不重演人物动作。

即兴资料引入新的目的地或带条件的候选线索时，先将新资料、玩家原请求和已完成步骤交回同一 KP，只安排剩余行动，再裁定实际对象与方法。程序不从新增线索的门槛拼装检定，不替玩家接受新条件。交接中的行动、裁定和出发前交谈各有恢复记录，普通交谈不增加这次调用。

复合请求的 `Plan.action` 只包含当前可执行段，`remaining` 保留原请求的后续意图与条件。仅有剩余意图时，原 KP 的叙述回复扩为 `ContinuedTelling`：`continuation.next` 提交一个即时计划，`pending` 交还玩家或保留待查事项，两者都空表示办完。下一计划必须已有足够资料，不能带一个尚未执行的 `lookup`。这不是完整工具循环：需要补查时保留意图，之后由 KP 结合新输入查明再安排；不暗中另调一次规划。

当前场面及其后续事件完整落实后，`Game.finish_request` 才原子安装下一段。每段有独立回合及恢复收据，原玩家发言只记录一次；六个生产入口通过 `engine.graph.stream` 续办，不在图内递归或提高步数限制。手掷、push 和遭遇继续使用原中断协议。普通单段不新增调用；原本只显示 NPC 对话的复合段需要一次 KP 判断，正文可为空。

自动续办前还须交接这段行动启动的异步世界工作。实际到场、求救等新情况先演出，再由同一 KP 更新下一步；异地私事不因此唤起主持或向玩家公开。后台的区间、事件起点和分阶段执行结果在启动前保存，断线后按持久记录继续，不依赖已经丢失的内存任务。计算等待不增加游戏分钟；同步世界模式不另启一份工作。这个屏障沿用原世界执行器，尚未解决独立分场时间与共享人物的区间占用。

暂停后的 `GameState.unfinished` 是本人私有意图笔记，不是自动队列，也不保留执行锁。KP 读到新输入后重新安排，采用的计划取代旧笔记；仍成立的意图明确留在新 `remaining`。笔记与 `last_actions` 不随联机状态发给客户端；普通原始输入、默认正文及其他骰类的完整私密投递另行完善。多人内部段沿同一窗口累积个人用时，整条请求结束或交还玩家时才消费原行动编号。

`Action.arrival_after_success` 默认关闭，表示抵达是否以本次主行动成功为前提。普通移动仍免裁定，“到书房再搜索”仍先抵达；突破阻拦、攀越后才能进入时，先在出发点裁定，成功才移动。这不强制掷骰。裁定的 `minutes` 只计前置尝试，成功后另计实际路程一次；失败、放弃不消耗成功路程、不触发目的地到访。幸运、孤注一掷和中断恢复沿用原行动及结算凭据，同行同意仍在出发前处理。沿途暂歇只到下一站，不提交终点的成功效果。

多人普通场面区分实际位置与主持焦点：独行仅移动行动者，其他同行组按自身位置保留。切换玩家不消耗路程或重新触发到访；人物资料、物件归属及现场目击按实际位置读取。当前仍是顺序处理各处行动，未完成的遭遇不能通过异地切换绕过，也未实现异地同时战斗。

| 项目 | 实现 |
|---|---|
| 对话历史 | harness：`GameState.transcripts`，按字符预算开窗，旧内容由摘要员折叠 |
| 思考强度 | harness：`Role.effort` 映射到各家自己的参数 |
| 结构化输出 | harness：厂商的 schema 模式或提示词 JSON，再做 JSON Schema 校验和一轮修复 |
| 工具调用 | harness：自己的 LangGraph 循环和沙箱工具，不用任何厂商的 tool calling |
| 联网搜索 | harness：Tavily / DuckDuckGo / Wikipedia，可以设成 `none` 离线 |
| 花费 | harness：按 token 估价，超预算就拒绝调用 |

主持、世界推演与人物对话按职责配置模型：

| 角色 | 职责 |
|---|---|
| `keeper` / `plan` 守秘人 | 掌握底牌，理解行动、安排现场主动行为、提交场面并叙述结果 |
| `world` 世界推演 | 集中处理本次被唤醒的 NPC，各自依据目标、知识与约定提出行动，逐人核对操作 |
| `npc` 人物对话 | 扮演正在交谈或主动参与的人物，一并提交台词与当场动作 |
| `director` 导演 | 调整节奏与冲突，补充模组未写的内容，提交完整场景方案 |
| `arbiter` 裁定 | 判断行动结果、检定条件及规则后果 |

未设置 `[roles.world]` 时，世界推演继承当前裁定角色的模型和思考配置，包括自定义路由；NPC 对话继续使用 `[roles.npc]`。世界推演会话按本次人物组命名为 `mind:<id>+<id>`，用量归入 `mind`，调用追踪标为 `world`；持久记忆来自世界记录。更换模型不会扩大任何 NPC 的知情范围。

## 随模型能力调整架构

模型升级后重新检查调用链，不把旧模型的补救措施当作永久架构。Anthropic 在 2026 年的[长任务 harness 实验](https://www.anthropic.com/engineering/harness-design-long-running-apps)中，随着模型能力提高，逐项移除了不再必要的任务拆分与中间评审；这些结果来自应用开发，不能直接证明跑团效果。AutoKeeper 据此采用的原则是：围绕实际失败增加约束，再用同一组场景检验它是否仍有必要。

KP 的意图理解、对话承接和现场裁定需要连续上下文，不为每个思考步骤另设角色。[OpenAI 的多智能体文档](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)也建议将短任务与依赖步骤留在主 agent，独立任务才交给子 agent。普通规划、整批规划、骰后配音工具和叙述现共用一个 keeper Session，历史、摘要和压缩只归这一会话。计划阶段仍使用其配置的模型、思考强度、输入限额及独立用量统计；切换传输不切换记忆。每次明确指定当前输出结构，Plan不会成为其他阶段的默认结构。裁定、检索与任意世界修改还没有统一到通用工具循环；战斗和追逐的专门规划沿原入口。裁定员不读取玩家原话或主持历史，NPC保留自身知识隔离。合并记忆不减少调用数，实际费用与等待仍需比较。

重要 NPC 持久保存身份、关系、知识、秘密与未完成计划。在场人物的主动参与由 KP 本轮安排；后台调度执行写定结果的日程，并在时间跳过、换场景或相关事件发生时集中处理需要判断的动向。同一时间片不再按人物或房间各调一次模型；前台已经参与的 NPC 也不会在同轮再次被后台安排。

有效的本轮 KP 安排同时负责当前现场保持沉默的人；不因他们没有列入主动对白清单，就另调幕后模型。后续世界推进读取当时的实际现场集合，离场者恢复幕后判断，固定日程仍走既有结算与待演路径。没有有效 KP 安排时保留原反应流程。此处不修改事件的反应属性，也不把未交接见闻标成已读；KP 的简报完整列出未完成与受阻计划、前置与完成条件及上次执行失败，不能只停后台而不交接职责。当前仍只接管主持焦点，不代表所有分场已有独立主持。

后台同次决策中的实际操作与完成确认共用一次原子提交。宿主在同一计划版本内先执行实际操作，再核对 `step done`，操作身份仍使用原输入索引；替换计划保留旧任务收尾的先后关系。预览、调度落地与待演提交采用相同顺序。完成条件与执行证据照常检查，任何一项无效则整组不落地，不因模型先列完成确认就反复调用，也不自动把受阻计划改成完成。

压缩用于延续会话，事件记录、物品归属与事实来源单独保留。[OpenAI 的记忆与压缩示例](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)同样区分工作上下文、可复用记忆和正式成果。这里的领域约定是：LightRAG 帮助查资料，时间表保存期限，世界记录保存事实；检索、摘要或角色台词都不能直接代替事实提交。

升级模型或调整流程时，先比较存档中的具体问题：省略指代、明确目的地、重要消息后的反应、谎言与真实物品、未落实即兴、故障恢复。固定片段对照与真实长局分开记录，保留版本指纹、任务结果、重复执行、调用次数和等待时间，便于判断应保留、合并还是撤除。离线回归可验证执行约束，不能代替真实模型的叙事与理解评估。当前真实 DeepSeek 主持的结果与尚存问题见[三模组连续试玩](playtest-three-modules-2026-10-23.md)，不以测试数量宣称体验或延迟已达到某个水平。

## 模型通道 `models.py`

| 后端 | 用法 | 结构化输出 | 思考 |
|---|---|---|---|
| `claude` | Claude Code（Claude Agent SDK）只当传输层：不给工具，`max_turns=1`，每次回复后在后台 `/clear` | `output_format` JSON Schema | `effort` |
| `langchain` · `deepseek:` | `ChatDeepSeek`，`base_url` 可改 | 提示词 JSON + `response_format: json_object` | `thinking.type` + `reasoning_effort`（low / high / max） |
| `langchain` · `ollama:` | `ChatOllama`，默认 `num_ctx=16384` | Ollama 的 `format`（受约束解码） | `reasoning`，只在 high / max 时开 |
| `langchain` · `openai:` / `anthropic:` / `google_genai:` | `init_chat_model` | 各家 schema 模式；带 `base_url` 的 OpenAI 兼容服务用提示词 JSON | `reasoning_effort` / `thinking.budget_tokens` / `thinking_level` |
| `codex` | Codex CLI（`codex exec`）同样只当传输层：用 `model_instructions_file` 换成我们的系统提示，只读沙箱，`--ephemeral` 不留会话 | `--output-schema`，schema 先转成 OpenAI 严格模式（对象封闭、字段全必填） | `model_reasoning_effort` |

Codex 通道每次调用都起一个新进程，实测约 9 秒（`gpt-5.6-luna`），Codex 自身固定带着约 8.5k token 的工具定义，关不掉。所以它更适合导入、生成这类不赶时间的任务，不适合实时回合。模型串写 `codex:<模型>`，`codex:default` 用登录账号的默认模型。

为什么要 `/clear`：同一个 Claude Code 进程里换 `session_id` 隔离不了上下文，实测会串到上一轮的内容；`/clear` 能清掉历史、保留系统提示，大约 0.4 秒。现在它在玩家读叙事的时候在后台跑，不占回合时间。

发给 Claude 的请求一条消息一个内容块，历史只往后追加。DeepSeek 按最长公共前缀自动命中缓存。Claude 只在请求标了缓存点的地方存前缀，而 Claude Code 只标请求末尾，也就是这一轮的新提示；新提示带着不进记录的一次性附言，下一次请求里不会原样出现，所以以前除了系统提示什么都命中不了：《有些人油盐不进》80 回合里，守秘人每次约 2.1 万 token，命中的始终只有 4,822。现在在历史的最后一块上加一个缓存标记，下一次请求会原样重发这一段，整段历史都能命中。固定 9 段剧情（`eval style`）里，第 9 次调用 88% 的输入来自缓存，以前每次只命中系统提示。标记默认 1 小时（订阅版 Claude Code 自己的标记也是 1 小时，短的不能排在长的前面），API 拒绝时降到 5 分钟，再不行就不标。

### 结构化输出

`Model.complete(schema=...)` 对所有后端的约定一样：

1. 有可靠 schema 模式的用 schema 模式（Claude、Ollama、OpenAI、Gemini）。没有的（DeepSeek、一般的 OpenAI 兼容服务）就把 schema 和一个自动生成的示例写进系统提示，并打开 JSON 模式。
2. 用 `jsonschema` 校验结果。
3. 不合格就把模型的原输出和校验器的报错一起发回去，修一次。
   纯文本任务可以直接接收文本；NPC 回复同时承担台词、约定、转交和知情记录，即使只有 `text` 必填也必须保留完整结构。DeepSeek 的 JSON 传输模式若只返回空白，格式修复可改用提示约束的 JSON 传输，仍用同一 schema 校验；不能把半份回应包装成台词、将动作默认为空。过去通过接受纯台词减少修复的试验曾丢失这些记录，现已撤回。
4. 仍不合格时按调用方处理。行动与裁定抛出可重试错误，不静默改成“不用掷骰”；游戏保留阶段记录供继续。

实测：本地 gemma4-31b 当裁定员时，第一次输出没通过 schema 校验，修了一轮就过了。

### 临时故障

每次调用都有超时（`AUTOKEEPER_TIMEOUT`，默认 600 秒）。

- **重试**：限流（429）、过载（529）、5xx、超时、断线都算临时故障，用 tenacity 指数退避加抖动，最多试三次。
- **不重试**：
  - 预算超限、认证失败、请求本身有错（400）；
  - 已经流给玩家的叙事，再重试玩家会看到同一段话出现两遍。
- **Claude Code 进程**：中途出错就丢掉这个进程，下一次重试换新的。
- **追踪**：重试次数写进追踪日志。

### 备用模型与熔断

每个角色可以配一个备用模型（`fallback`），比如 DeepSeek 后面挂一个本地 Ollama。

- 主模型重试用完仍失败，或者超了预算，这次调用交给备用模型。
- 配置的输入字符预算超限属于本地请求拒绝，不触发备用模型或熔断；切换后端不能绕过该限制。
- 失败的模型冷却 5 分钟（熔断）：这期间所有用它的 Agent 都直接走备用模型，不再各自等重试和超时；5 分钟后再试主模型。
- 叙事已经流给玩家一部分时不降级，否则同一段话的开头会出现两遍。
- 降级时界面弹一条提示，追踪里那次调用记 `fallback_for`。

实测：把主模型的地址指向一个没人监听的端口，备用模型是正常的 DeepSeek。守秘人的调用重试三次（`OpenAIConnectionError`）后交给备用模型，一共 9.9 秒；紧接着 NPC 的调用直接走备用模型，1.2 秒。

## 上下文 `context.py`

`Session` 是一个 Agent 的对话。对话记录是调用方持有的普通列表，游戏里就是 `GameState.transcripts[key]`，跟存档一起保存。每次调用把窗口完整发一遍：

| Agent | 窗口（字符） | 说明 |
|---|---|---|
| keeper | 16,000 | 叙事要前后连贯 |
| npc:\<id\> | 8,000 | 每个 NPC 一份，只有自己的对话 |
| investigator:\<id\> | 6,000 | AI 调查员记得自己刚做过什么 |
| arbiter | 4,000 | 看到最近几次裁定，不会重复给线索 |
| intent / chronicler / vision | 0 | 无状态，需要的东西都在提示里 |

记录超出窗口时，最早的几轮交给摘要员（`summarizer` 角色，用便宜的模型）并进 `GameState.notes[key]`，之后作为窗口的第一条消息出现。`Role.window` 可以按模型改窗口，比如本地小模型改小一些。

`window` 管理历史折叠；可选的 `max_input_chars` 限制整次已知文本输入，默认 `0` 表示不设置硬限制。统计包括系统提示、历史、摘要、固定任务、本次消息、临时附言、输出 schema 及 JSON 格式说明；schema 不重复计数。字符数与 UTF-8 字节数分开记录，不推测模型 token 窗口，也不包含图片或后端传输包装。

```toml
[roles.world]
max_input_chars = 120000
```

发送前超限时，有可压缩历史的会话最多尝试一次摘要，保留最近一组完整问答。摘要失败或仍不能满足预算时恢复原文与原摘要，并拒绝本次请求；当前不可压缩资料已超过限制时直接拒绝。无状态调用不会压缩其他角色的记录。模型直接调用、摘要调用及格式修复请求也各自执行预算检查，已发生的调用按实际用量记账，未发送的修复不收费。

折叠在后台进行，回复先交给玩家，下一次调用前才等折叠完成。实测摘要员一次要 6 秒左右，这样玩家不用干等。

- **顺序**：先拿到新摘要，再一起删旧记录、写摘要，中途存档不会丢内容。
- **摘要失败**：保留完整原文；不通过截断内容强行继续。

`send(prompt, remember=...)`：这次发完整的提示，记录里只存精简版。裁定员每回合的提示带着场景、线索表和整张人物卡，约 1,500 字，原样记下的话 4,000 字的窗口两回合就满，摘要员几乎每两回合就要折叠一次。现在裁定员只记“行动 + 地点”，AI 调查员只记“几点、在哪”，场景每回合都会重新给。前缀缓存不受影响：DeepSeek 命中到最后一条之前，Claude 命中到历史末尾的缓存标记。

普通KP安排也使用同一机制：记原话、人物／地点／行动编号及尚未执行的草案，实际查询另记问题与返回资料，修正另记未落实原因。NPC工具阶段只追加新回执；近期完整内容和当前现场仍在实际调用中提供。`send(..., model=...)`可仅为当前阶段选择模型传输，测量与硬限使用该模型，摘要窗口和后台压缩仍由原会话负责，不临时替换会话对象。

`send(prompt, extra=...)`：`extra` 只用于本次调用，不进入会话记录，可携带操作失败的具体原因与修正要求。NPC 的知识范围由输入资料控制，普通对话不再使用字符比对后删句的泄密检查。

`keeper` 读取模组真相、前史、结局与主持规则，以及当前世界记录生成的幕后简报。当前改写过的真相、结论和前史也会送入，以本局版本为准。KP 可以知道秘密，公开叙述仍须遵守调查员实际可感知的信息范围。

KP 的行动安排读取近期连续经过、时间与来源、约定和实际持有物，并可点名查询不足的记录或原文。摘要必须区分亲历、听说和推测，邀请与计划不能压成已完成行动。出发前的交谈保存在 `Action.before`，同行还需由 NPC 回应或场面操作实际落实。

裁定员读取结构化行动、本地守秘人资料、线索原文和人物处境，不读取玩家原话。主持所需的原文可通过 LightRAG 按需检索，结果作为私有资料使用；已有设定改写时仍可检索，当前改写附在结果后面，注明以改写为准。

KP 报告同时保留公开的裁定目标 `Ruling.why` 和 `Turn.primary` 指定的最终主检定；观察、用物等非社交行动也使用这份范围。事件自己的骰不覆盖主结果，尚未结算的附带行动保持待定。骰前主动安排只作未执行的候选，由 KP 结合骰后结果选用；NPC 工具只接收 KP 指定的可感知后果，不接收整份私有裁定依据。实际台词、操作、听见者与未落实原因随后返回 KP，表演原话也保留实际受众。

NPC 台词与动作一并输出，物品转交、移动、同行和承诺等操作先做确定性检查，失败时修正一次。普通对话不再默认另调模型做叙述语义核对；措辞与泄密问题通过离线评测和开发者排查观察。导演改写等其他任务仍有自己的验证流程。

NPC 的 `text` 是实际投递内容，不是全知剧本。每次调用明确当前收件调查员，私聊与分开行动都会更新；未被听见的密谈不附原话，心境、真实计划与欺骗说明沿用既有私有字段。程序不扫描台词判断哪些句子该删，也不因角色主动公开某个计划而拦截。

裁定与场面提交使用实际物件引用。本地操作清单附物件 id、完整名称、归属与数量；NPC 只收到自己持物的编号。拿起、交出、归还和放置进入归属操作，状态备注不代替转交，交物不代表消耗。新日常物件先明确实际拿出者，再说明交给谁或留在哪个已登记地点。程序不从旁白反推物件变化。

多人整批安排将全局与各人的近期记录合并去重，保留原话和收件范围；每个地点只附一次场面，再逐条附行动者、持物和原话。NPC 已在角色资料或动态知识中完整给出的事实，只另附来源与知识引用；已给出的亲历事件不再抄入第二个近期栏目。KP 的完整底牌、本地规则和原有记忆窗口不因此缩小。

输出 schema 去掉嵌套节点的自动标题，使用紧凑 JSON。根标题供模型适配器命名，实际字段、说明、约束、引用与完整示例全部保留，返回值仍用原 schema 校验。三种后端共用此表示；输入预算与追踪也按新表示计数。字符减少不是实际 token 或费用的等比例下降。

`/kp <说明>` 直接形成场外提问，不调用行动解析或裁定，不消耗游戏回合和时间，也不取走等待呈现的导演结果。叙述按公开上下文答复；该通道不提供隐藏信息或直接修改状态的权限。

### 缓存与思考强度

DeepSeek 的前缀缓存按思考设置分开存。同一段约 4,000 token 的前缀，先用 high 调一次，再换设置调第二次：

| 第二次调用 | 命中缓存的 token |
|---|---|
| 还是 high | 3,840 |
| 换成 low | 0 |
| 关掉思考 | 0（关思考的请求有自己的一份缓存，再调一次命中 3,840） |

所以每个角色的思考强度固定不变。摘要员和守秘人强度不同，摘要请求本来就用不上守秘人的缓存；摘要也用不着推理，DeepSeek 预设里就把摘要员的思考关了。

记录员（读档时的前情回顾）同理。同一个存档各测两次：

| | 第一个字 | 讲完 | 输出 token |
|---|---|---|---|
| 开思考（low） | 3.8 s / 1.6 s | 5.6 s / 3.4 s | 1,311 / 950 |
| 不思考 | 0.5 s / 0.5 s | 2.0 s / 2.1 s | 768 / 772 |

回顾的内容不受影响，读档后几乎立刻开口，所以记录员也不思考。开着思考的那次还把提示里的 Markdown 加粗照抄了出来，现在提示里写明只输出纯文本。（当时的回顾还是评书腔，后来按玩家的反馈改成了平实的前情回顾。）

### 模式：整体升降一档

`--mode 高级剧情` 让讲故事的四个角色（守秘人、导演、NPC、AI 调查员）多想一层，`--mode 经济` 让所有角色少想一层；单独设过思考强度的角色不动。“一层”按后端真正分得清的档位算：DeepSeek 只有 low、high、max（medium 按 high 跑），所以守秘人的 high 在经济模式下降到 low，而不是降到等于没变的 medium；Claude Code 不传强度时用它自己的默认档，不一定比 low 少，所以最低到 low。

同一个模组用 DeepSeek 自动跑 12 回合，每种模式一局：

| 模式 | 用时 | 花费 | 思考 | 守秘人 p50 | NPC p50 | 导演调用 / 落地的方案 |
|---|---|---|---|---|---|---|
| 经济 | 123 s | $0.033 | 17.4k 字 | 2.2 s | 1.1 s | 2 / 2 |
| 标准 | 127 s | $0.032 | 21.3k 字 | 2.0 s | 2.3 s | 1 / 1 |
| 高级剧情 | 208 s | $0.054 | 60.0k 字 | 2.8 s | 4.2 s | 3 / 3 |

DeepSeek 的账单大头是输入 token，思考占得少，所以经济模式省时间不省钱。第一版经济模式连导演也关掉思考，结果开局之后 5 次调用只有 1 个方案通过校验，其余都白调了，这局花了 $0.039，比标准还贵。现在导演最低保留 low。

## Agent 循环 `loop.py`

导入模组、生成模组、考据核实都用同一个循环：

```text
START → think ─┬─ finish ─────────→ END
          ↑    └→ act ─┬─ 步数上限 → END
          └────────────┘
```

模型每一步只输出一个扁平的 JSON：`thought`、`tool`，再加上这个工具要用的字段（`path`、`content`、`old`、`new`、`query`、`url`、`start`、`limit`）。任何后端都能产出这个格式，所以不需要厂商的 tool calling。

- 工具的错误（路径越界、参数缺失、原文不唯一、搜索失败）作为观察结果回给模型，由模型自己改，任务不会因此中断。
- 观察结果最多 12,000 字；最后 5 步会提醒模型收尾。
- 会话带一个工作摘要员：旧步骤被折叠成进度摘要（目标、已完成、关键事实及出处、写过的文件、还没做的事）。
- 导入任务还要求模型把要点记进 `notes.md`，作为长期记忆。

### 工具 `tools.py`

| 工具 | 作用 |
|---|---|
| `ls` `read_file` `grep` | 读工作区（带行号分段读，正则搜索） |
| `write_file` `append_file` `edit_file` | 写工作区；`edit_file` 要求原文唯一 |
| `view_image` | 读图员（vision 角色）看图回答，所以 Agent 自己的模型可以只认文字 |
| `check` | 在进程里跑模组校验器 |
| `web_search` `fetch_url` | 联网搜索，网页用 MarkItDown 转成 Markdown 分段读 |

工作区（`Workspace`）把路径解析到根目录之下，越界直接拒绝。写入只允许落在白名单里，导入时是 `module.yaml`、`notes.md`、`art/*`；校验通过后由程序把草稿整理成模组目录（`module/package.py`）。

### 搜索 `search.py`

`auto`：有 `TAVILY_API_KEY` 用 Tavily，否则用 DuckDuckGo（`ddgs`），再不行用 Wikipedia。`none`：工具直接告诉模型“联网已关闭”，考据卡全部标“未核实”，之后联网了可以用 `autokeeper research` 补核。

## 导演：模组没写到的地方

导演（`agents/director.py`）负责添加模组之外的人物、地点和事件。守秘人叙述、裁定与 NPC 对话使用已经确认的资料，新增内容经校验后才进入本局：

- **开局改编**：读调查员的背景（重要之人、意义非凡之地、信念），把一两样织进故事；补生活和关系，保留原作的矛盾，不强制预埋额外冲突或新的催促时限。
- **展开**：裁定员判断这次行动“动机正常、模组没写到”（`Ruling.scope = 可即兴`），导演就加新地点、新 NPC、新线索或一段演出，并让它指回主线；偏离太远时可以加一个新结局。
- **后果**：裁定员判断行动违背年代或能力时，导演说明实际限制。离开主线、求助和寻找捷径本身不构成惩罚理由；伤害与损失必须有已经成立的风险。
- **千钧一发**：玩家接受灵感检定且检定失败时，按规则准备能辨认出遗漏线索的险境。连续 12 回合没有进展记录只给 KP 一条内部参考，由它判断是否确实卡住；不会自动调用导演、催促玩家或增加危险，日常交谈不触发这条参考。

导演读取中立行动、本局设定和世界记录。方案先校验引用、数量、线索条件、插件和幕后操作，不合格时带问题修正一次。当前行动依赖的方案仍不成立时，保留该行动并提示重试，不先掷骰或消耗时间。通过的模组改动、世界操作和插件来源整批提交，不能丢掉失败的幕后部分后单独发布剧情；等待期间世界发生变化时重新准备。原模组文件不动，方案保存在 `GameState.improv`。

几条配套规则：

- **角色弧光**：NPC 多了一个 `arc` 字段，记着此刻的心境和变化，每次开口时作为一次性提示带上，不进它的记忆。
- **线索发放**：依本次行动、实际在场人物和模组前提决定能得到什么，不按条数拖延。引擎检查引用、取得条件和实际来源，不设每轮固定条数。检定失败就是没拿到，不论是不是关键线索：裁定员在 `on_fail` 写模组明说的失败结果（失败也能找到、打碎了东西），在 `on_push_fail` 写孤注一掷再失败会怎样，玩家选之前就看到；引擎照字段结算标记、耽搁、受伤和模组允许的线索，再告诉守秘人这次尝试了什么、没拿到什么、发生了什么（`Game._failed`）。
- **守秘人**：按已结算的行动与导演方案描述结果。日常可以平静结束；悬念、压力和线索应有情境依据。

实测（DeepSeek，《追书人》，同样六个行动跑两遍）：

| 导演的思考强度 | 调用 | 延迟 p50 / p95 | 输出 token / 次 |
|---|---|---|---|
| high | 7（含一次修正） | 23.4 s / 46.7 s | 约 3,800 |
| low | 2 | 13.3 s / 24.8 s | 约 2,800 |

开局改编和当前行动依赖的即兴会显示“KP 正在构思…”，等方案与必要首图就绪后继续。未涉及眼前行动的推进可在后台准备，由 `Game.interlude` 呈现；玩家接近相关场景时先完成交接。模型等待不推进游戏时间，重试复用已校验方案、读取版本和提交凭据，避免重复创建剧情。`Action.echo` 仅为旧数据兼容字段，不能把尚未结算的玩家意图提前显示成动作。

以下为旧版不等待导演策略的历史测量，不代表当前版本的延迟（未重新进行付费实测）：

| | 改之前 | 改之后 |
|---|---|---|
| 开局开讲 | 约 30 s | 3.4 s |
| 第一句回应 | 守秘人开口时 | 1.4–2.2 s |
| 守秘人开口（普通回合） | 4–6 s | 3.3–8 s |
| 守秘人开口（即兴回合） | 13.7 s（等导演 6 s 仍没等到） | 5.4 s |
| 即兴的后续 | 下一回合 | 回合结束 9.5 s 后插曲上演，讲 2.5 s |

开局改编把哈罗德背景里的老搭档奥马利写成了介绍他来的熟人，安排了一个上门催着宣告死亡的律师（第一天 15:00）和第二天夜里的一场大冲突；在 1922 年“掏手机报警”被演成“手伸进风衣内袋，只摸到烟盒、几枚硬币和半包口香糖”，杂货铺老板从此起了疑心。DeepSeek 预设里导演用 low。`improv = "严格"` 关掉这一切。

## 车卡 `agents/card.py`

模型负责判断，规则交给代码。AI 协助车卡收到的是一句描述（带“的”、列了几样特点、或者比较长）时不上网，直接按描述出题；收到名字时先查资料：维基百科只认同名词条或重定向（搜索结果里提到这个名字的页面不算），查不到就用网页搜索的摘要和前两个结果页里提到这个人的段落；照片来自维基首图、网页图片搜索和 Commons，由玩家挑，挑照片这一步顺便确认找对了人。模型出三个问题（在这个年代他是谁、侧重什么本事、再加一个按人定的问题），然后给出一份草稿：属性怎么分、用哪个职业点公式、点数加在哪。`rules/creation.make` 按 7 版规则落实：属性必须是 80/70/60/60/50/50/50/40 各用一次（不对就按草稿的强弱顺序重排），职业点和兴趣点超了按比例缩，技能最高 90，克苏鲁神话不能买，每处修正都告诉玩家。

玩家带来的卡不重建。骰娘的 `.st` 指令由代码解析，八项属性齐了就以代码读到的数为准，不调模型；表格、PDF、Word、纸质卡照片由模型照原样录入，`rules/creation.accept` 只修正不可能的值（属性超出 1–99、技能超过 99），卡上写的当前理智和 HP 照留。酒馆角色卡没有数值，按人设走出题流程，卡上的图当照片。

实测（DeepSeek，立石凛，模组《追书人》）：查资料 9 s（维基那次被限流，靠网页搜索的 7 条资料认出她是 MyGO!!!!! 千早爱音的声优），出题 10 s，建卡 19 s，按“射击加到 60、改成 28 岁”修改 11 s；导入一张文字人物卡 11 s，修改 2 s，数值一个不差。

## 叙事偏好与文风

玩家的叙事偏好（篇幅、恐怖程度、节奏、略去细节的内容）只有固定选项，每轮作为守秘人的一次性 `extra` 发出，不进记录，系统提示不变，前缀缓存不受影响；选项都是默认值时提示词和以前完全一样。导演即兴不碰雷区，NPC 说到时含糊带过；裁定员和行动解析器收到的提示词逐字节不变，测试里断言过。

文风上，守秘人提示里的反面清单（“不要问你要做什么”“不煽情”）改成了正面说法，keeper-craft 加了两段示范叙事。`autokeeper eval style` 在《追书人》上固定 8 回合的行动、裁定、NPC 台词和骰子，只让守秘人真调用；`eval cliche` 数套话密度。DeepSeek flash，每种条件 3 遍：

| 条件 | 守秘人思考 | 前五项套话 / 千字 | 全部套话 / 千字 | 比喻“像” / 千字 | 每段的段落数 |
|---|---|---|---|---|---|
| 改前 | high | 0.64 | 0.85 | 4.04 | 3.5 |
| 示范初稿 | high | 0.47 | 0.47 | 3.55 | 1.8 |
| 定稿 | high | 0.42 | 0.42 | 3.16 | 3.4 |
| 经济模式，改前 | low | 1.15 | 1.38 | 4.83 | 2.9 |
| 经济模式，定稿 | low | 0.20 | 0.41 | 5.70 | 3.4 |

改前的提示词本来就很少出套话，变化在 3 遍样本的噪声以内，不能说示范有效。示范初稿写的是坐火车到站，3 次开场里有 2 次照抄了火车站，段落也从 3.5 掉到 1.8；定稿拆成两段、换成游戏中段的场景，并注明摘自别的模组，这两个问题都没再出现。

固定脚本评测现显式提供 `Plan`、NPC 回复及披露，先通过真实回复流程落实，再评剩余叙述。它只比较文风，不衡量生产 KP 是否正确选择 NPC 或工具。完整主持链的结构化往返、恢复与私密投递使用另一组引擎回归；不能将两种评测的通过互相替代。

## 局域网联机 `net/`

房主那边跑一个 Hub（`net/hub.py`，aiohttp websocket）。它持有唯一一份模组、状态和 Agent，按座位顺序推进同一张回合图；每块玩家屏幕只是客户端（`tui/screens/net.py`），收事件、发行动，界面和单机共用一个 `GameScreen`。

- **座位**：每位调查员是玩家座或 AI 座。轮到 AI 座时 AI 调查员行动，轮到玩家座就等那位玩家的输入。玩家掉线时，Hub 往他的输入队列里放一个空值，这一回合交给 AI；他坐回来以后，下一回合又由他行动。
- **孤注一掷和幸运**：回合图在检定失败时用 LangGraph 的 interrupt 停下，Hub 只把选项发给正在行动的玩家；AI 座按它行动时说好的做法孤注一掷（没说做法就用幸运或放弃），掉线的人用幸运或放弃。
- **普通检定的读者**：产生检定时保存当时现场的调查员名单，首骰、幸运、push、放弃和无效重掷沿用这份名单；实时结果、历史骰、完整检定记录与重连快照使用同一范围。设置 `public_rolls = true` 可向全桌公开普通骰值及技能，但不公开原行动全文或孤注一掷风险。设置用于新开局或重新载入，已存在的检定不扩大范围。此项不代表整轮私密行动已经贯通，原始行动输入、默认KP正文及其他类别的骰仍需各自接入。
- **客户端拿到什么**：事件照原样转发，线索、移动、时间、理智这类会改状态的事件之后补一份状态快照。快照里没有 Agent 的对话记录、守秘人笔记、用量和导演的方案；模组是脱敏副本，没有真相、守秘人须知、NPC 的心思、事件和结局的正文，没找到的线索和手稿只剩编号，找到时随事件补全。导演加了地点和人物，Hub 先发一份新的副本，再发即兴事件，事件里去掉导演的理由。
- **房间**：标题画面「多人游戏 → 开房间」（`tui/screens/host.py`）和 `autokeeper host` 开的是同一种房间（`net/room.py`）。Hub 在自己的线程和事件循环里跑，回合和模型调用不占界面的循环；房主自己的界面和朋友一样连 127.0.0.1 的 websocket，带着房间密钥进来就是房主。房间活到房主关掉它或退出程序。
- **准备房间**（`tui/screens/lobby.py`）：座位、每位调查员的头像和整张卡、谁坐在哪，都来自 Hub 的 welcome 里那份脱敏模组和状态；房间信息（`Hub.room`）列出房主机器的每个 IPv4 地址，`ifaddr` 列网卡，按网卡名和网段标出局域网、Radmin VPN（26.x）、ZeroTier、Tailscale，容器、虚拟机和代理的 TUN 不列。
- **网页**：一个单独的进程（`python -m autokeeper.net.web`），textual-serve 给每个浏览器标签在房主机器上起一个 `autokeeper join 127.0.0.1` 进程，朋友什么都不用装。页面用自己的模板（`net/page/app_index.html`）：琥珀暗色，中文等宽字体（载入 textual.js 时换掉它写死的 Roboto Mono），地址跟着访客输入的走，经虚拟局域网打开的也连得上。网页进程的 stdin 一关就退；关房间时先关网页，访客的游戏有 3 秒退出，再停 Hub，所有 websocket 当场关掉。
- **测试**：`tests/test_net.py` 用真实 websocket 和一套立即应答的假 Agent，覆盖抢座、抢答、场外聊天、掉线由 AI 代打、终端界面从大厅入座到行动，以及客户端拿不到真相和导演的理由；`tests/test_room.py` 覆盖从标题画面开房间到入座、关房间，准备房间显示的内容，网页进程，以及 `autokeeper host`。

## 录制与回放 `replay.py`

`autokeeper autoplay DIR --record game.jsonl` 用真实模型跑一局，按顺序录下每个 Agent 的每条回复、规则掷的每一颗骰子，最后记下这局的结果：线索、剧情标记、去过的地点、时间、结局、每人的 HP 和 SAN。

`--replay game.jsonl` 把录像放一遍，不调用任何模型，不需要密钥，也不联网。每个 Agent 按顺序拿回自己录下的回复，骰子掷出同样的点数，整条回合流水线（行动解析 → 裁定 → 规则结算 → NPC → 守秘人 → 记忆）真实地跑一遍，最后比对结果。

- **按 Agent 和顺序对上，不比对提示词**：改提示词的措辞不会让录像失效。
- **引擎多调用一次模型、多掷一次骰子，回放立刻报错**（`CassetteError`），不会悄悄跑偏。
- **结果对不上，测试失败**：引擎改动有没有改变剧情走向，一测就知道。

仓库里带着一盘用 DeepSeek 录的样例模组《钟楼》（8 回合，36 条回复、3 次检定，18 KB），CI 在三个系统上回放它，0.6 秒。另有一个测试故意让引擎每次检定前多掷一颗骰子，确认回放会当场报错。

## 预算与追踪

- `spend.py`：按 token 估价（DeepSeek 按峰时价，所以估高不估低）。配置了 `budget_usd`，超出后按量计费的调用全部拒绝。账本在 `data/spend.json`。几个进程可能同时花钱（比如自动跑团和 TUI 一起开），所以每次记账都持文件锁读改写，写完用原子改名替换，读的人看不到写了一半的文件；账本真坏了就挪成 `.bad` 留证据，不会悄悄从零记起（要是从零记起，预算护栏就形同虚设）。测试里 4 个进程各记 40 笔，一笔不丢。
- `trace.py`：每次调用一行 JSON，写进 `data/logs/traces/<日期>.jsonl`。记录运行编号（进程，或 autoplay 的存档名）、版本、Agent、后端、模型、思考强度、输出方式（text / native / json）、输入字数、token、缓存命中、思考字数、耗时、修复和重试次数、是否降级、错误；上下文的 `schema_format` 标识结构表示。`AUTOKEEPER_TRACE=full` 还会记下完整的提示、输出和思考内容。
- 每局开发者记录由 `engine/observability.py` 追加保存，达到分段大小后使用递增编号归档，不覆盖旧段。网页的正序读取、历史翻页与调用查询包含全部分段，游标跨轮转和读档延续；仅当前文件为空不等于此前没有记录。
- `autokeeper trace`：把追踪按 Agent（或模型、后端、运行）汇总成表：调用、输入、缓存命中、输出、延迟 p50/p95、花费，并在汇总行单列未命中缓存输入；出现过修复、重试、降级、错误时自动多出这几列。`--run last` 只看最近一次运行，`--runs` 列出每次运行。

### 用追踪找到的问题

用 DeepSeek 自动跑《追书人》（两名 AI 调查员，最多 80 回合），`autokeeper trace --run <存档名>`：

```text
  Agent          调用     输入   缓存     输出   延迟 p50/p95      花费
  keeper           81   834.9k    84%    14.9k       2.0/2.9s   $0.0615
  investigator     80   338.0k    67%     7.5k       1.2/2.0s   $0.0435
  intent           80    74.2k    57%    15.9k       1.5/2.9s   $0.0290
  arbiter          75   332.5k    77%    18.4k       1.9/3.2s   $0.0468
  summarizer       56   194.9k     2%   114.5k      6.7/25.6s   $0.1950
  ...
  合计            408    1.84M    69%   193.8k       1.8/8.8s   $0.4108
```

摘要员的调用只占 14%，花费却占 47%。拆开看有两个原因：

1. 它的输出一半以上是思考 token（思考 16.8k 字，正文 9.7k 字）。摘要用不着推理，而且因为上一节说的缓存分区，开着思考也换不来缓存。
2. 它被叫得太勤：裁定员的长提示原样进记录，4,000 字的窗口两回合就满。

修法：DeepSeek 预设里关掉摘要员的思考；裁定员和 AI 调查员改用 `remember` 只记精简版。

同一局还暴露了一个回合图的问题：调查员说“我走到陵墓石门前看门缝”，行动解析器把它当成原地调查，地点一直停在公墓。裁定员其实看出来了，它的理由写着“陵墓本体属于相邻场景”，但裁定结果里没有能挪动队伍的字段。结果陵墓里的线索和隧道永远拿不到，80 回合都没走到结局。现在去别处做事时 `destination` 照填，裁定员按目的地的场景来裁，引擎结算时先移动。

修完重跑，53 回合打到结局“最后一晚”。两局走的路线不同，所以按每回合比较：

| | 修之前（80 回合，没到结局） | 修之后（53 回合，到结局） |
|---|---|---|
| 每回合花费 | $0.0051 | $0.0029（−43%） |
| 每回合的摘要调用 | 0.70 | 0.26 |
| 摘要员占总花费 | 47% | 16% |
| 摘要员延迟 p50 / p95 | 6.7 s / 25.6 s | 3.1 s / 6.7 s |
| 全部调用的 p95 延迟 | 8.8 s | 4.5 s |
| 去过的地点 | 5 / 10 | 10 / 10 |

## 换模型

```bash
uv run autokeeper doctor --ping                        # 每个角色走哪个模型，密钥齐不齐，实际发一句测通
uv run autokeeper --preset deepseek                    # DeepSeek：flash，思考强度按分工
AUTOKEEPER_MODEL=ollama:qwen3:14b uv run autokeeper --search none   # 全部本地、完全离线
uv run autokeeper --preset deepseek --fallback ollama:qwen3:14b        # DeepSeek 出问题或超预算，就换本地模型
```

```toml
# autokeeper.toml 或 ~/.config/autokeeper/config.toml
preset = "deepseek"
budget_usd = 5
search = "auto"
minds = 2                    # 重要 NPC 在幕后一回合最多想几次（长时间跳过翻倍），0 只照计划走（docs/world.md）

[roles.keeper]               # 单个角色单独改
backend = "langchain"
model = "deepseek:deepseek-v4-pro"
effort = "high"

[roles.world]                # 可省略，省略时跟随最终的 arbiter 配置
backend = "langchain"
model = "deepseek:deepseek-flash"
effort = "high"

[roles.all]                  # 对所有角色生效，比如自建的 OpenAI 兼容服务
base_url = "http://localhost:8000/v1"
fallback = "ollama:qwen3:14b"  # 备用模型；不带前缀的 claude-* 走 Claude Code
```

密钥从环境变量读（`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`GOOGLE_API_KEY`、`ANTHROPIC_API_KEY`），也会读 `~/.config/autokeeper/.env` 和仓库根目录的 `.env`（已被 gitignore）。

### 文件放在哪里

所有位置都由 `src/autokeeper/paths.py` 给出，别的代码不自己拼路径。从源码目录运行时，游戏写的东西都在仓库根目录的 `data/` 下（设了 `AUTOKEEPER_HOME` 就在那个目录下，布局和仓库一样）；装成命令（`uv tool install autokeeper`）以后，同样的内容放在用户目录：`data/` 换成 `~/.local/share/autokeeper/`，`cache/` 换成 `~/.cache/autokeeper/`，导入的模组在 `~/.local/share/autokeeper/modules/`，Windows 见[游玩指南](playing.md#东西放在哪)。规则书和守秘人卡组放在 `rule/`（源码目录里，或装成命令后的 `~/.local/share/autokeeper/rule/`），不进 Git。自带的模组、共用的 Skills 和掷骰脚本随包一起装好，掷骰组件的 npm 依赖装在 `~/.local/share/autokeeper/bridge/`。

```text
data/
  games/          存档 <slot>.json、index.json、checkpoints.sqlite
    art/          本局生成的图、联机玩家传来的头像
    rooms/        正在开的联机房间的密钥
    trash/        删掉的存档和角色卡，挪回去就能恢复
  cards/          自己的调查员
  角色卡导出/      导出角色卡的默认位置
  cache/          可以整个删掉，用到时重建
    models/       本地向量模型（约 90 MB）
    kb/           各模组的 LightRAG 知识库；kb/rules/ 是规则书的检索索引
    art/          各模组缺图的地点、人物、物件和怪物找到或画好的图
    cards/        读入的守秘人卡组
    showcases/    各模组的大场景图
    pictures/     照片的预处理副本，画面上显示的是它
    sessions/     Claude Code、Codex 进程的工作目录
  logs/           traces/<日期>.jsonl、stderr.log、web.log
  preferences.json  tips.json  spend.json  imagegen/<模组>.json
```

界面里改的设置在 `~/.config/autokeeper/settings.json`（Windows 是 `%APPDATA%\autokeeper\`）。评测报告、自动跑团记录和公网分享的运行文件在 `dev/output/`（装成命令后是 `~/.local/share/autokeeper/dev-output/`）。

从源码目录写存档时，会把这个目录记进 `~/.config/autokeeper/checkouts.json`；装好的命令第一次运行时，把这些目录和当前目录里的存档、角色卡、导入的模组和慢的缓存复制过来（`paths.adopt`，不移动、不覆盖），`autokeeper migrate <目录>` 可以随时再带一次。

### 同一局中途换厂商

游戏里按 F9 可以换预设、换所有角色的模型、设备用模型。换的时候只是给每个 Agent 新建通道，对话记录本来就在存档里，新模型接着用。

实测（《追书人》，一名 AI 调查员）：

1. DeepSeek 跑了 3 回合（20 秒）：问托马斯叔叔最后一次被人看见是什么时候，进书房拿到日记和“书架上的空档”。
2. 换成本地 gemma4-31b（Ollama）再跑 2 回合：叙事接得上，又拿到“松动的窗锁”。
3. 换完之后，问守秘人“到目前为止去过哪里、问过托马斯什么、拿到哪些线索”：两个地点、托马斯的回答（一年前九月的一个星期二）、三条线索都答对了，其中两条是 DeepSeek 那段拿到的。
4. 问 NPC 托马斯“刚才调查员问过你什么”，他用角色的口吻答：“您刚才问我叔叔最后一次被看见是什么时候，我告诉您是一年前的某个星期二。”这句话是在 DeepSeek 上说的。

回忆提问用的是 `send` + `forget()`，问完就从记录里删掉，不影响后面的游戏。追踪里这一局按模型分：DeepSeek 12 次调用，p50 1.7 秒，$0.0045；gemma4 10 次调用，p50 19.2 秒，免费。
