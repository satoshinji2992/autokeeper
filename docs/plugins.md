# 规则插件

规则插件用于实现通用引擎尚未覆盖的玩法，例如按日结算风寒、仪式倒计时或密码锁。插件状态由程序保存并更新。

插件可在模组编译、游戏中的即兴扩展，或开发者模式的 `Ctrl+K` 家规入口中生成。所有插件均须通过自带测试后才能启用。

## 目录结构

```text
module.yaml                        # plugins: [my_rule]
plugins/my_rule/manifest.json      # 名字、版本、hooks、能力、动作、初始状态、测试
plugins/my_rule/plugin.py          # def handle(event, ctx, api)
```

`handle` 接收事件、上下文（时间、地点、调查员、剧情标记、本插件的状态）和宿主 API，返回新状态和一组效果。接口细节和例子在 [插件接口](plugin-api.md)。

## 事件

| 事件 | 触发时机 |
| --- | --- |
| `start` | 第一次启用 |
| `turn` | 每次行动和时间推进之后 |
| `visit` | 到达某个地点 |
| `action` | 守秘人在单次行动的定案中调用插件声明的自定义动作 |
| `command` | 玩家输入了插件注册的斜杠命令 |
| `answer` | 玩家提交插件交互的答案 |
| `timer` | 插件设定的计时器到期 |
| `roll` / `clue` | 一次检定之后 / 找到线索之后 |

重复触发条件和时间条件由插件自行判断。

## 效果

基础效果：属性变化、状态、伤害、理智、剧情标记、解锁线索、公开叙事。HP/SAN、重伤、疯狂仍按原有规则结算。

附加效果：

| 效果 | 用途 | 限制 |
| --- | --- | --- |
| `panels` | 在右栏显示文字、进度条、列表、表格或字符画 | 每个插件 2 页，每页 12 行 |
| `show` | 在场景图上叠加演出，或插入叙述区 | 12 帧、20 秒内；每个插件每轮一段 |
| `prompt` | 提供选择、填空、数字、排序、点选或棋盘交互 | 同一时间每人一道；一局最多 30 步 |
| `timer` / `schedule` | 按游戏分钟、轮数或某个时间点触发 | 每个插件 8 个 |
| `item` | 增加或移除物品 | |
| `hint` | 向守秘人提供本轮叙述需包含的提示 | 每次一句，80 字以内 |
| `attitude` | NPC 对调查员的态度变化 | -3 到 3 |

另外，manifest 里可以用 `commands` 注册最多 3 个斜杠命令（比如 `/占卜`），不能和自带命令重名。

使用限制：

- 面板和演出默认向所有玩家显示；设置 `to` 后仅向指定调查员显示。题目仅向作答者显示，公开内容不得包含未公开的秘密。
- 题目在这一段叙述结束后才弹出。玩家跳过或超时按默认答案算；AI 调查员和空着的联机座位当场按 `ai` 策略作答。默认答案不要设成正确答案。
- 演出可通过点击或 Esc 跳过；关闭动画后仅显示最后一帧。
- 订阅了 `answer`、`timer`、`command`、`roll`、`clue` 的插件，每种事件至少要有一项测试，否则无法加载。
- 即兴导演每局最多写 6 个插件，升级已有的不算。

## 改核心规则

插件不只在规则结算之后追加效果，也可以改核心规则本身。manifest 的 `rules` 列出它回答的判定：成功等级、难度与奖惩骰、孤注一掷、幸运、理智损失、伤害、人物卡派生值、结局成长、一次成长检定。游戏执行相应判定时，先计算核心规则的结果，再将输入和结果交给插件。插件返回需要修改的字段，未返回的字段保留核心规则的结果。

- 一个判定只能有一个启用的插件回答，两个插件回答同一个判定会在载入和 `autokeeper check` 时报错。
- 答案按核心字段校验，字段不存在或类型错误时，整份结果无效，保留核心规则结果，并暂停插件、记录原因。判定须在 1 秒内完成，超时按相同方式处理。
- 规则钩子里只能用 `track`、`flag`、`hint`、`note` 四种效果，不能 `api.roll`；需要掷骰时，应先返回 `dice` 骰式列表；宿主完成掷骰后通过 `event.dice` 传入结果，第二次调用必须返回最终判定。只在结算阶段里可用。
- tests 要为每个回答的判定各写一项。
- `rules_text` 是写给模型的一小段规则，放在核心规则之后，标明以这里为准。
- `serves` 只有自成一个规则体系的共享规则包写：`system`（模组 `system` 字段的标签）、`names`（别的叫法）、`title`（提示词里对规则的称呼）、`core_skill`（模型读的核心规则 skill，空为 CoC 7 版）、`characteristics`、`skills`、`sanity_kinds`、`weapon_facts`（模组要写的属性、技能名、理智来源的类别、武器 facts 的键）和 `writing`（给写这种模组的人的说明）。导入器据此判断原文能不能挂这个包，并把这些要求读给导入模型；`autokeeper check` 据此核对模组。模型在局内写的家规插件不写它。
- `tracks` 在每个调查员的人物卡上记插件自己的数值（点数池、普通数、分项分数），只有该插件的 `track` 效果能改。点数池可以用 `stands_for`（`hp`/`mp`/`san`/`luck`）顶替人物卡上的一行，换名字显示；不写就另起一行。
- 模组在写理智损失的地方（线索、事件、怪物、草图、守秘人的理智检定与代价）可以写 `sanity_kind`，一个自由的短词（暴力、无助、非自然……），核心规则不看，规则插件在 `sanity_effect` 的 `kind` 和理智检定的 `roll` 事件里读到。模组的攻击可以写 `{line: 攻击那一行, facts: {键: 值}}`，伤害判定的 `weapon.facts` 原样带着它。
- 输出里的 `keeper` 是只给守秘人看的一条私有记录（比如隐藏的腐化值），不会发给任何玩家。`unreal` 效果为某位调查员启用或停用幻觉，核心规则只在疯狂时允许幻觉。

## 共享插件

模组的 `plugins: [id]` 先找模组自己的 `plugins/<id>/`，找不到再找随程序提供的共享插件。同一个插件可以被多个模组使用，存档里照常保存它的源码。

## 示例：追书人的旧书架

`modules/zhuishuren/plugins/shujia/`。找到〔书架上的空档〕后，右栏多一页「旧书架」。在书房输入 `/理书架`，按道格拉斯目录卡上剩下的三句话把四本书排回原位。排好后托马斯对调查员会亲近一点，守秘人下一段会提一句。它不给线索，不排也不影响查案。

```bash
autokeeper plugin test modules/zhuishuren
```

## 家规

开发者模式下在 `Ctrl+K` 里写一句话，比如“每过一夜要吃一顿饭，不吃 HP 减 1”或者“加个和店主猜数字的小游戏”。系统生成插件与测试，通过沙箱测试后才会安装。家规只存在这一局的存档里，不改模组文件。测试未通过时会显示原因，可修改规则描述后重试。

联机时只有从标题页开房间的房主在自己的游戏画面里有开发者模式，可以查看、暂停插件和加家规；家规在当前一段讲完后由房主电脑生成、测试并安装。其他玩家和观战者没有这个入口。

## 玩家看到的

- 开发者模式下，`Ctrl+K`（或 Esc 菜单 → 设置里的“规则插件”）列出每条规则：做什么、改了哪些核心规则、能尝试什么、插件声明可公开的状态（比如“风寒：第 2 天”）、最近的效果，以及暂停的原因。
- 规则生效时，叙述区会显示带插件名的提示。
- 插件声明的动作会出现在输入框补全和 F5 行动建议里。玩家还是用平常的话描述行动，由守秘人决定调用。
- 联机玩家按各自的接收范围查看叙述提示与右栏页面。源码、私有状态和报错细节仅保存在房主设备。

## 沙箱

模型生成的插件代码在玩家设备上执行，受以下沙箱限制：

1. 运行前检查语法树：不能 import，禁止访问双下划线属性、帧和全局变量，不能用 `getattr`、`eval`、`exec`、`compile`、`open`，仅允许使用白名单中的内建函数。
2. 在独立的 Python 子进程中执行（`-I -S`），清空继承的环境变量，避免通过环境变量获取 API 密钥。
3. 子进程通过审计钩子阻止文件访问、网络访问、创建子进程和导入。POSIX 上另有 CPU、内存和写文件的限制；Windows 上在超时后强制终止进程。

代码长度、输出、状态大小、运行时间和掷骰次数都有上限。插件出错只暂停它自己。状态、源码版本和执行记录跟存档一起保存，读档恢复同一回合时不会重复扣除数值。

## 命令

```bash
autokeeper plugin list <模组>              # 列出插件和自定义动作
autokeeper plugin test <插件目录或模组>     # 在沙箱里跑测试
autokeeper check modules/<id>              # 检查模组时也会跑插件测试
```

标题页的“设置”里可以整体关掉规则插件。
