# 2026-10-22 Token 使用审计

审计基线：`a299bfb`。本轮仅统计本机已有存档、调用记录和历史源码，未调用付费模型，未读取凭据或输出原始游玩对话。末节另列本轮正在实施的结构序列化优化，尚无其上线后的真实游玩数据。

## 结论

现有真实记录中的输入负载确实很高。今晚 Linux《冬雪之下》14 轮，排除视觉任务后累计 **1,096,206 input、468,712 非缓存输入，56 次调用**；含开局均摊，每轮约 **78,300 input、33,479 非缓存输入、4 次调用**。

普通安排、守秘人叙述和裁定占主要输入。固定提示及结构定义占请求字符的比例很高；世界决策也是一个大合同，但本段仅调用四次。视觉生成需要独立统计，短局开场的集中配图尤其显眼。

本地能够精确核算 schema、规则提示、模组资料、历史和检索内容的**字符数**，供应方只回报请求整体 token。Claude SDK 的额外包装没有单独的 token 明细；图片、tokenizer、缓存建立等也不能由字符串长度反推。每次约两万 input 的记录是真实总量，但目前不能把其中多少归为 Claude 隐藏包装，或证明某后端把同一段文字放大了几倍。

不能据此宣称“0.0.5 比 0.0.3 贵几倍”：没有同一模组、模型、游玩输入与缓存条件下的对照。本机实录均早于 `c747f5e`、`a299bfb` 晚间提交；它们能说明近期运行负载，不能证明最新批次增加了多少实际消耗。

还检查了其他工作区。`consist/data/logs/traces/2026-10-22.jsonl` 的六次调用均为 importer，不纳入运行时。旧目录包含大量自动游玩、重放、评判和编译调用，也全部排除。S1 在 release 中有一份相同存档，不能累计两次。

- `input` 包含提供方上报的缓存读取；**非缓存输入 = input − cache_read**。该差值可能包含缓存建立，不直接等同账单金额。
- `output` 使用提供方回报；Codex 的记录还合计 reasoning 输出，不能当成玩家可见文字长度。
- 存档 `usage` 用于总账，debug `call` 用于关联角色、会话与轮次。同一次调用也会写入全局 trace，不能重复相加。
- 单条 trace 的 `repairs` 可包含额外请求且 usage 已合并；不能把调用行数当作全部供应方请求次数。
- 失败记录没有 token 字段表示未获得统计，不证明提供方没有消耗。缓存统计缺失也不能擅自补成命中。
- 下文“每轮”是存档总额除以轮数，含开局准备；短局不能代表长局稳态。存档没有代码提交号，日期与字段形状不足以确认精确版本。

## 检索、格式修复与重试

### S2：近期 Claude 实录

- 60 条 debug 模型调用包含四次视觉调用；非视觉 56 次与存档总账吻合。
- JSON 格式 `repair = 0`；Arbiter 有两次传输层 retry，已经包含在相应结果统计中。
- 第 3、7、8 轮各出现一次场面快照拒绝，并各多生成一次 Keeper 回复。这三次额外输入合计 **66,432**，其中缓存 **58,684**、非缓存 **7,748**。约占本段非视觉 input 的 6.1%、非缓存输入的 1.7%，需要优化但不足以解释全部负载。
- 有 13 条 retrieval 记录，返回 context 全为空，也没有 `lore` 模型调用。记录“检索过”不等于额外调用了 13 次模型。

### S3：Codex 实录

20 条导演失败请求未返回 token；其中开局和第 2 轮各十条。该局发生在 `cdaafbf` 的“模型拒收不反复重试”修复前，不能再算作当前代码仍固定执行的行为。失败日志之外，存档视觉生成本身已经占 44.6% input。

普通 Plan 八次中，只有五次为日常安排，另有一次开战、两次遭遇安排。Codex 每次开启临时进程，其输入可能包含供应方隐藏包装；例如本段 Progress 的可见文本总计 2,049 字符，回报 input 为 12,071 token。仅凭该差值无法精确分离包装、tokenizer 和其他服务端内容。

### S4：13 轮 DeepSeek 实录

92 条完成记录中有 **11 次 JSON 格式修复**：Keeper 九次、Plan 一次、Mind 一次；另有五次场面拒绝、两次摘要调用，以及一次明确的 Plan 查询续调。该样本有人类和 AI 调查员混合参与，不与 S2 作严格比较。

两次 summarizer 合计 3,117 input；世界决策 18 次、183,613 input；Keeper 19 条记录、337,579 input，其中许多已合并格式修复用量。优化时需要分别识别格式失败、场面操作校验和真正的追加主持任务，不能把它们统一叫“agent 太多”。

## 优先节省的位置

1. **先压合同包装。** 本轮已做不改变合同含义的序列化收紧。随后再考虑按场景启用结构分支：普通调查无需每次携带全部遭遇效果，但不能因省字段使 KP 无法登记真实行为。
2. **保持稳定前缀与实际缓存。** 分角色观察命中率、首次调用与后续调用。Codex 的频繁冷调用需要单独评估，不能用它的零命中数据估算 DeepSeek 或 Claude 的稳态。保持 KP 对底牌和原始记录的访问。
3. **复用视觉成果。** 按角色拆出理解、生成、校验的次数，保留原模组图片和有效缓存，检查同一对象是否反复准备。用户要求即兴图片，验收应是图片可用且不过量重复，不是关闭图片。
4. **只在有工作时安排世界判断。** S2 的四次合理幕后调用未构成主要负载；S4 的十八次则值得对照触发依据。准备写好的日程继续由代码执行，在场主动行为由当前主持安排。
5. **减少无效重写。** 保留物理操作和检定一致性；格式问题与状态问题分别记录原因。一次纠正应只重做失败阶段，不重复付费、掷骰和已成功交谈。不要新增模型审批以“优化”现有模型输出。
6. **摘要随后优化。** 本段摘要占比很低；先大量削减记忆会影响角色承接，并不能明显解决固定 schema 负载。

下一轮验收应固定模组、模型、角色配置、阶段与缓存状态，选择几段实际游玩问题进行短轮比较；分别报告初始化与正常回合、角色与会话、非视觉与视觉、缓存读取与建立、恢复与格式修复。本轮已为新 trace 增加 `version`，上下文标记 `schema_format = compact-v1`，以区分新旧格式；旧记录不能据此补出原版本。后续仍可补代码提交号、存档、行动编号和现场编号，减少靠日期猜测的空间。

本报告证明了输入规模与固定合同负担，尚未证明本轮优化后的实际节省金额，也不以减少调用数代替跑团质量验收。
