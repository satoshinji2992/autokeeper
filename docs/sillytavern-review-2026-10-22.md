# 0.0.5 剩余工作、运行限制与酒馆参考

2026-10-22。AutoKeeper 审查基线为 `de65510`；SillyTavern 使用官方 release 分支 `06bde939fb1e9c4c8d8641d810f0a916b5bce127`（package 1.19.0）。本轮为代码和官方资料研究，未运行酒馆代码、安装依赖、调用付费模型或修改游戏配置。下文区分现有行为与建议。

## “导演预算”的准确含义

C2 所说的预算是**同一无效方案的修正次数**：初稿及一次修正都不成立后停止。它不是金额，不是整局只让导演工作两次。代码没有导演整局调用次数上限；`expanded` 仅作诊断记录，没有展开冷却。

修稿遇到服务故障时保留具体问题和已返回草案次数；取消、读档继续原任务。真实世界变化导致方案过时，重新准备另一份方案，服务恢复与图片等待另计。

### 当前限制清单

| 项目 | 当前行为 | 判断 |
| --- | --- | --- |
| API 累计费用 | 默认无上限；本机 Linux 配置文件写有 `budget_usd = 10` | 按当前数据目录的本地账本累计估价，限制已识别的计费后端；不是账户余额或每局额度。未读取 .env，不把文件值冒称所有运行实例的有效设置 |
| 单次输入 | `max_input_chars` 默认 0，未启用硬字符限制；角色历史有各自压缩窗口 | 历史窗口与整次输入上限分开解释；不能靠省掉 KP 底牌制造节省 |
| NPC 幕后判断 | 默认普通轮两批，长时间跳过四批；每批可因查询追加发送 | 调用工作量限制，不能解释成一人两次，也不限制 KP 当场安排 NPC 主动行为 |
| 草案修正 | 初稿＋一次修正 | 保留，防止同一错误无限重开；不可丢失错误反馈 |
| 场景等待 | 300 秒；首图恢复最多两次 | 服务期限不等于游戏时间；图片失败可后台补，不把已提交动作重做 |
| 可选预备并发 | 两份 | 当前玩家必需的准备不受此名额阻断 |
| 重要人物记录 | 整体最多六个，固定日程的被动人物也占用 | 不合理。应限制活跃模型工作量，人物动机与日程记录应能完整保存 |
| 导演新增大场景画面 | 整局三个，超出后截掉 showcases | 不合理的固定视觉名额；静默丢掉尤其不利于排查。并非普通剧情事件只能发生三次 |
| 图片 | 默认 24 次尝试、视觉估价 1 美元；另有每存档 12 张新 AI 图、同模组跨所有存档及导入累计 100 张 | 多重限制需整合成明确可调设置，保留缓存和原图。这里不限制模组原图的正常展示 |
| 新增插件 | 导演六个、总数八个，单方案一个 | 按实际资源与用途评估，避免把功能数量当作整局质量控制 |
| 单份新增内容 | 普通方案最多 4 人／3 地点／5 线索／4 事件；开局更宽 | 防止异常大输出有意义；小方案应作为通常偏好。提示词仍写更低名额，需统一，不能因此把合理人物组合拒绝掉 |

主要依据：`harness/spend.py`、`config.py`、`engine/game.py`、`world/scheduler.py`、`world/ops.py` 的 Enlist、`engine/showcase.py`、`imagegen.py`、`engine/visuals.py`、`module/improv.py` 和 `agents/director.py`。只读脚本已复现第七个被动日程人物被六人上限拒绝。

本轮未擅自取消费用设置。应把**费用设置、失败修正、并发量和内容名额分别命名**，由用户选择资源开销，移除没有剧情依据的整局人物和画面配额。

## 0.0.5 还缺什么

同场私语、KP 个人文字观察、多人共同安排、按人累计耗时、现场补登记与战后救援已经实现。独立改写审批、固定轮数强制离场、重复上下文与无效草案重开已处理。不能把这些已完成项继续列成当前缺陷。

| 优先级 | 尚缺内容 | 玩家能感受到的验收 |
| --- | --- | --- |
| P0 | 普通检定的重试和成功后操作 | 无线索奖励的开锁、维修等，仍能在适用时选择孤注一掷或幸运；改判成功后真正开门、交物或改变状态 |
| P0 | 清理人物记录名额及静默丢内容 | 模组人物、日程和 KP 的合理安排不因六人／三画面等固定名额遗失；实际资源不足有明确记录 |
| P1 | 浏览器笔记持久化与导出 | 刷新、重连后恢复本人笔记，按游戏及座位隔离 |
| P1 | 个人结果和材料完整贯通 | 私人检定、手稿、地图及图片和文字使用同一受众，晚加入和重连仍只得到自己的内容 |
| P1 | 真正独立的并行现场 | 医院、图书馆能同时持续交谈；各自保留时间、待办和恢复记录，电话、共享 NPC、物品争抢按实际因果交接 |
| P2 | 玩家之间共同结算的竞逐 | 有底层对抗规则，但还需把双方声明、争夺目标和共同结果串起来，网络先收到不等于角色先抢到 |
| 发布前 | 模组与导入贯通、旧档／安装／重连、真人短轮对照 | 日记未发现、酒未交付、私下得知情报等条件不提前兑现；意图理解、行动兑现、信息范围、等待和费用均可核查 |

普通检定缺口可直接定位：`engine/game.py` 的检定选择由非空的可得线索列表放行；待选记录主要保存线索与标记。重试成功后也主要结算这两项，尚未完整保存原行动的交物、装备、会合和通路变化。不能只删掉线索条件而不补齐成功操作的恢复。

私人结果仍使用全局 `clues/handouts`；普通骰子与材料事件没有通用的私有行动范围。现有私信已避免解锁公共地图，但不等于每人已有完整个人地图。`Hub._settle_round` 仍逐条运行，`Game.resolve` 仍使用全局结算锁；共同窗口取最长耗时不能处理两组独立推进和跨场时间交接。详见[并行现场设计](parallel-scenes-0.0.5.md)。

## 酒馆值得借鉴的实现

下面先列它确实实现的行为，再列 AutoKeeper 的建议；建议尚未接入。

### 上下文分项与实际请求检查

PromptManager 可展开消息角色、正文与 token 信息，itemized prompts 按人物、世界书、摘要等来源分项。[消息检查源码](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/PromptManager.js#L1425-L1463)、[分项源码](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/itemized-prompts.js#L109-L132)。

AutoKeeper 已有完整调用记录与输入大小分解，可继续细分为底牌、场景规则、近期原话、世界记录、检索和输出结构，并标明资料来源、为何纳入或未纳入。这能判断“模型没遵守”还是“根本没有给它”。本地 token 估算与服务方真实 usage 保持区分，无需再加排查审批模型。

### 按角色与任务组织资料

世界书先处理角色等筛选、关键词与触发条件，再处理条目的持续生效和预算准入。数据银行也区分全局、角色和当前聊天的资料范围。[世界书源码](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/world-info.js#L4782-L4912)、[资料范围说明](https://docs.sillytavern.app/usage/core-concepts/data-bank/)。

可借鉴场景与人物资料的明确归属和生效范围：当前事项未结束时保留，结束后退出临时上下文。KP 的底牌和权威记录照常可用；NPC 先按知情权限筛选，再检索。不能因为文字提到“日记”就注入尚未成立的发现结果，也不能用词命中代替编译期的前置条件。

### 近期原话与旧记录去重

向量扩展保护近期消息，检索旧消息时按 hash 去重，并从参与组装的历史中去掉已另行注入的同一内容。[实现](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/extensions/vectors/index.js#L806-L854)。

本项目 C2 已做多人和 NPC 内部去重，下一步可核查“会话历史、世界简报、原文检索”是否反复带入同一来源。优先保留近期完整交谈、约定和未完成行动；远期细节可检索。相同措辞若属于不同人的说法或不同事件，不能只因文本相同而合并。

### 摘要绑定明确的覆盖范围

酒馆把摘要存到具体消息，消息变化时恢复仍有效的摘要；后台生成结束会检查聊天是否已经改变。[恢复逻辑](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/extensions/memory/index.js#L419-L472)、[结果检查](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/extensions/memory/index.js#L742-L751)、[摘要锚点](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/extensions/memory/index.js#L964-L987)。

可把摘要标明现场、受众、事件范围与版本；恢复时确认仍适用，原记录保留。摘要是便于延续主持的资料，不能改写世界事实。若提供剧情分支或回退，须恢复对应世界和操作记录，不能只改旁白而保留另一条分支的物品与骰子结果。

### 用示例表达人物语气

酒馆支持角色示例对白，且将人物定义与示例分开。[角色设计说明](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)。

编译可准备少量符合原作认知的语气示例，例如人物对陌生人、可信伙伴和异常征兆的不同反应；不把示例变成每轮必演的固定台词。不再通过“总先咳嗽”“每次反问一句”来定义人设，角色的具体反应仍交给看到充分上下文的模型。

## 不应直接照搬

酒馆自然群聊用点名、talkativeness 随机和无人时随机补人确定发言者；激活后仍逐人等待生成，聊天历史在群成员间共享。[自然顺序](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/group-chats.js#L1242-L1309)、[逐人生成](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/group-chats.js#L1051-L1069)、[共享历史说明](https://docs.sillytavern.app/usage/core-concepts/groupchats/)。

本项目可以借“谁还未参与”的提示，由 KP 决定合适时机；人物主动性依据动机、关系、所知和未办完的事。多现场需要真正独立的上下文与结算，不能用逐角色轮换代替，也不能把全组私密历史共享给所有人物。

世界书 sticky／cooldown／delay 按消息数计，超预算可省略整个条目。[计时源码](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/world-info.js#L604-L610)、[预算准入](https://github.com/SillyTavern/SillyTavern/blob/06bde939fb1e9c4c8d8641d810f0a916b5bce127/public/scripts/world-info.js#L4993-L5076)。AutoKeeper 应按现场、游戏时间和事件条件维护相关事项，不重新引入“聊两轮 NPC 就必须走”或“固定轮数强制催剧情”。

## 建议的体验优先级

先修影响选择的检定缺口和会丢记录的名额，再补笔记与个人结果，随后完成两个独立现场的最小通路。场内让人物根据动机主动承担事情，既有约定到换场景后仍能兑现；日常交流可以顺利进行，危险按模组与实际行动发展。重要发现用具体可感知内容交代，玩家自己判断意义。

开发者模式优先借上下文分项、来源去重与摘要范围。它们直接对应当前开销和可排查性；不新增常驻智能体或运行时删句机制。最后用相同模型的短段真人存档重放和真人试玩验证语境承接、人物反应、失败后果、等待与费用，沿用已有 2010 项程序回归作为状态与恢复基础。
