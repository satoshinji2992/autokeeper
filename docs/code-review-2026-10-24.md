# 代码审阅：联机执行、世界记录与异常恢复

本报告保留审阅时的故障与证据；后续修复及新的联机流程记录在[多人行动实现](multiplayer-turns-2026-10-24.md)。下文的“未修复”描述对应审阅基线，不代表后续开发状态。

审阅基线：`codex/multiplayer-live-audit`，`f71cd88`。本轮只新增审阅文档与离线回归证据，没有修改生产代码、运行中的房间或真实存档，没有付费模型调用，也没有发布或推送。

## 结论

本轮确认 **12 类仍未修复的独立缺陷：2 项 P1、10 项 P2**。这是本次范围内的下限，不是整个仓库的缺陷总数。同一原因的多个表现合并计算：例如存档索引并发覆盖和写入中断归为一项；热汤与钥匙误匹配也归为一项。

此前修复的 `Gateway._publish` 向 `SceneView.__dict__` 写入字段、造成现场状态脱节的问题没有重复计数。新发现的跨等待对象替换问题与它有关，但触发机制和需要修复的地方不同。

目前不能据此称联机体验已稳定：失败后的场景仍可能占住时间，另一个场景因而无法推进；记录与多视角输出也存在静默丢失。继续叠加叙事检查或提示词约束，解决不了这些问题。

## P1：优先处理的阻塞与存档问题

### 1. 无人接手的失败回合没有释放时间占用

- 位置：[`net/hub.py:1886`](../src/autokeeper/net/hub.py#L1886)，正常释放位于 `engine/graph.py` 的 `remember` 节点。
- 触发：AI 席位或已经断线的玩家执行行动，已预留时间，随后 KP 持续报错；自动重试耗尽后 `_unattended` 放弃回合。
- 缺陷：清了 `pending_turn`，没清现场的 `reservation`。这个现场没有可恢复回合，却仍被当作占用时间与资源。
- 实测：实际执行一分钟行动后连续失败，另一个现场的二十分钟行动持续等待；旧现场不能自动衔接，也不能手动允许时间通过。存档往返仍保留占用。旧现场再做一轮行动可能覆盖残留，因此不是永远无法恢复，但玩家需要猜测隐藏条件。
- 修复：完成、放弃、取消都调用统一的收尾函数，保留已经结算的事实，结束票据并唤醒等待方；不能只清重试记录，也不能把放弃误报为成功。
- 证据：`test_review_multiplayer_lifecycle.py::test_abandoned_turn_releases_its_reservation_and_unblocks_the_other_scene`。

### 2. 存档索引缺少原子写入与并发保护

- 位置：[`tui/library.py:42`](../src/autokeeper/tui/library.py#L42)、[第 54 行](../src/autokeeper/tui/library.py#L54)；存档列表读取位于 [`tui/screens/saves.py:64`](../src/autokeeper/tui/screens/saves.py#L64)。
- 缺陷：存档正文使用临时文件替换，索引却直接覆盖；读取、修改、写回也没有锁。
- 实测一：两个独立写入者同时保存不同槽位，两个正文都存在，索引只剩其中一个。这要求并行进程或线程，不代表同一事件循环里的同步保存天然并发。
- 实测二：注入写入中断后，原本有效的索引变成损坏的 JSON。继续调查列表返回空；后续自动保存读取索引时也会报错。正文仍在，不应描述为所有存档内容已经消失。
- 修复：所有索引修改共用带跨进程锁的原子更新；索引损坏时可以从存档正文重建。重命名、删除和复制也应使用同一路径，避免各写各的。
- 证据：`test_review_remaining_ui.py` 的并发保存与中断写入两例。

## P2：状态、消息与恢复问题

### 3. 世界提交替换调查员对象，跨等待结算写到旧对象

- 位置：[`world/tools.py:370`](../src/autokeeper/world/tools.py#L370)，实际调用经过 `Game.push → _pushed → Cast.repush`。
- 触发：一个现场等待孤注一掷裁定时，另一个现场 NPC 交给调查员一件物品。
- 实测：孤注一掷成功，旧对象获得侦查成长标记，正式存档里的调查员没有这个标记。整份 `investigators` 被替换，等待中的代码仍持有旧引用。
- 修复：提交时保留持久实体的身份，或等待后按 ID 重新获取再修改。不要把“同一事件循环中提交没有 await”当作跨任务引用安全的保证。`World.load` 已有原地恢复实现，可对照使用。
- 范围：已证明成长标记丢失，没有证明 HP、SAN 或幸运也丢失，不据此扩大结论。

### 4. 取消的时间协调被当成已经完成

- 位置：[`net/scenes.py:70`](../src/autokeeper/net/scenes.py#L70)、[第 87 行](../src/autokeeper/net/scenes.py#L87)、[第 111 行](../src/autokeeper/net/scenes.py#L111)。
- 触发：KP 正在考虑场景时间衔接，玩家声明行动，取消这个调用，随后又撤回声明。
- 实测：场景已经空闲，时间协调也被允许，但去重标记仍在；再次请求同一时间不会再询问 KP，别的现场继续等待。
- 修复：区分明确拒绝与取消、失败。未得到结果的调用应恢复可重试状态，避免无期限去重，也避免无间隔重试浪费调用。

### 5. 游戏结束标志只更新主房间，子现场继续接收行动

- 位置：[`net/scenes.py:24`](../src/autokeeper/net/scenes.py#L24)、[`net/hub.py:488`](../src/autokeeper/net/hub.py#L488)。
- 缺陷：子现场复制了 `over=False`；主房间结束后，消息仍先路由到子现场。
- 实测：结局后 `.en` 进入没人消费的即时队列，普通行动也继续排队，没有结束反馈。
- 修复：房间生命周期使用单一来源；结束后由根路由处理成长等允许的命令，明确拒绝新行动，并收尾子现场任务。

### 6. 点了观战，服务器仍认为玩家占着原座位

- 位置：[`tui/screens/lobby.py:562`](../src/autokeeper/tui/screens/lobby.py#L562)。
- 缺陷：只把界面的 `chosen` 改为空，没有通知服务器释放座位。
- 实测：实际本地连接与 Textual 界面中，界面进入观战状态，`hub.sits[原座位]` 仍是同一连接。其他人无法入座；服务端也不会按离座处理接管。
- 修复：增加明确的离座请求与确认；确认后切换观战并更新座位、准备和接管状态。

### 7. 入房超时只覆盖建立连接，不覆盖房间确认

- 位置：[`tui/screens/lobby.py:156`](../src/autokeeper/tui/screens/lobby.py#L156)、[`net/link.py:42`](../src/autokeeper/net/link.py#L42)。
- 触发：服务端接受 WebSocket，却没有返回 `welcome`。
- 实测：将超时缩短后，本地静默端点保持连接，界面仍停在没有座位的大厅，超过期限也不返回或提示失败。
- 修复：入房完成应以收到有效 `welcome` 为准，连接与确认共用期限；超时关闭连接并恢复操作入口。

### 8. 物件子串匹配直接采用第一个候选

- 位置：[`world/ops.py:120`](../src/autokeeper/world/ops.py#L120)、[`world/adapters.py:141`](../src/autokeeper/world/adapters.py#L141)。
- 实测一：NPC 给“热汤”，程序匹配“一锅热汤”，把整锅转交。这也是原局出现过的现象。
- 实测二：同时持有钢钥匙、黄铜钥匙时，说交出“钥匙”，换一下记录插入顺序就交出另一把；重要物件也会被选中。
- 修复：明确 ID 优先；名称匹配必须检查是否唯一，多个候选交回 KP/NPC 确定。容器、份量与同类物品不能靠字符串包含关系直接视为同一实体。

### 9. 交出一件同名物品，会把另一件的背包显示也删掉

- 位置：[`world/ops.py:297`](../src/autokeeper/world/ops.py#L297)。
- 实测：两把不同 ID 的“钥匙”都在调查员身上，按准确 ID 交出一把，背包里的“钥匙”整行被删；另一把在世界记录中仍归调查员。
- 区别：这次使用了准确 ID，与上一项模糊名称解析不是同一个问题。
- 修复：持有关系以实体 ID 为准，背包显示从当前持有关系派生；至少删除名称前检查是否还有同名物件归该调查员。

### 10. 物件可以被提交成自己的持有者

- 位置：[`world/ops.py:283`](../src/autokeeper/world/ops.py#L283)、[`world/store.py:154`](../src/autokeeper/world/store.py#L154)。
- 实测：真实 `Cast.npc` 的 `items` 回复把钥匙交给钥匙自身 ID，校验与提交均成功；随后查询该物件位置触发递归错误。
- 修复：按工具说明限定接收者类型，拒绝自身归属；若要支持容器，再检查归属链无环，位置查询也应识别坏链。
- 范围：证明了坏状态能落盘、位置查询会失败，没有证明提交瞬间必然导致整个房间崩溃。

### 11. 空白摘要仍被提交，旧记忆与公共原话一起丢失

- 位置：[`engine/game.py:3655`](../src/autokeeper/engine/game.py#L3655)。
- 实测：49 条记录触发压缩，摘要返回空白，旧摘要被清空，日志缩到 24 条；前 25 条公共原文没有进入存档的历史记录。
- 修复：摘要生成成功、内容有效后再提交替换；失败保留旧摘要与原文。`harness/context.py` 已有空摘要保护，不必另造一套。重要事实的原始依据也不应只靠调试文件保留。

### 12. 场面纠正的最终路径丢弃私密叙述和配图

- 位置：[`engine/game.py:5412`](../src/autokeeper/engine/game.py#L5412)。
- 触发：两次场面校验未通过，第三次输出合法的纠正终稿。
- 实测：完整回合图中，终稿含合法收件人的私密观察与存在的手稿图片，程序却只取 `.text`。没有私密叙述或配图事件，存档往返后也没有相应文字和展示记录，重连不能补回。
- 修复：纠正终稿仍使用完整的分受众输出，保留其中合法的私密文本、媒体及继续行动信息；不能直接复用前两份被拒稿的内容。

## 共性与实现取舍

这些问题集中在四处，不需要为每一处再加一个 agent：

1. **主房间和子现场的状态归属不清。** `SceneTable` 继承整个 `Hub` 并复制其 `__dict__`，共享对象会同步、标量却留在旧值。应明确哪些状态属于房间、哪些属于现场，用属性访问根状态；不必为此重写整个联机层。
2. **成功路径完整，失败、取消和结束路径缺少收尾。** 时间占用、去重标记、队列消费和回合记录必须一起处理。应补统一的小型收尾函数，而不是在异常分支各清一个字段。
3. **事实实体与展示名称混用。** 名称可以给玩家看，提交、归属和数量应依赖稳定 ID。不要继续靠字符串包含关系增加“智能匹配”。
4. **降级时只保住正文，忽略正式记录和投递。** 摘要、私密观察、图片都需要完整的成功提交条件。模型调用结束不等于领域任务完成。

KP 仍应拥有完整资料和修改世界的权限。本轮没有把它远程登记设定、玩家数值同步或会合跳时间列成缺陷；这些需要遵守已经决定的产品行为。程序应保证记录真实、操作可恢复、消息送对人，而不是通过更多删句和审批限制 KP。

## 建议修复顺序

1. 先收尾失败回合的时间占用，修存档索引。两项都可能阻止继续游玩。
2. 修跨等待对象替换、时间协调取消、根/子房间结束同步以及离座确认，恢复多人执行的一致性。
3. 修物件匹配、同名库存和循环归属，避免新局继续产生错误数据。
4. 补摘要提交、完整纠正回复和入房确认超时。
5. 在临时存档上连续验证：三人分场 → 一人断线/接管 → KP 输出失败 → 恢复 → 会合 → 存读档 → 结局成长。单项测试通过后，再证明这条连续路径成立。
